# Prompt

If I created an Agent in code and hosted it in AWS but I want that agent available to users in my company's Azure tenant. How do I go about registering the app on Azure Entra. Show me the steps in detail.

# Response

## Registering an AWS-Hosted Agent in Your Azure Entra Tenant

Your agent runs on AWS, but your users and identity governance live in Microsoft Entra. The key insight: **you register the agent's identity in your Entra tenant and use Federated Identity Credentials (FIC) to let your AWS-hosted code authenticate without storing Entra secrets on AWS.**

> **Important:** Agent identities can only be issued tokens in the Microsoft Entra tenant where they're created. They can't access resources or APIs in other tenants.
> — [Agent Identities](https://learn.microsoft.com/en-us/entra/agent-id/identity-platform/agent-identities)

---

### Prerequisites

Before you begin, ensure:

1. **Microsoft 365 Copilot license** with **Frontier program** enabled in your tenant
   - Sign in to [Microsoft 365 admin center](https://admin.microsoft.com) → **Copilot** → **Settings** → **User access** → **Copilot Frontier** → Enable
2. **Entra roles assigned** to the person performing setup:
   - **Agent ID Developer** or **Agent ID Administrator** — to create blueprints and identities
   - **Cloud Application Administrator** — for delegated permission grants
   - **Privileged Role Administrator** — for application permission grants
3. **Microsoft Graph beta endpoint** — all Agent ID operations use `/beta` during preview
4. **An AWS OIDC Identity Provider** configured in your AWS account (for federated credentials — detailed in Step 3)

---

### Step 1 — Create an Agent Identity Blueprint

The blueprint is the registration template in your Entra tenant. It defines *what kind of agent* this is.

Connect to Microsoft Graph PowerShell:

```powershell
Install-Module Microsoft.Graph.Beta.Applications -Scope CurrentUser -Force

Connect-MgGraph -Scopes "AgentIdentityBlueprint.Create", `
  "AgentIdentityBlueprint.AddRemoveCreds.All", `
  "AgentIdentityBlueprint.ReadWrite.All", `
  "AgentIdentityBlueprintPrincipal.Create", `
  "User.Read" -TenantId <your-tenant-id>
```

Create the blueprint via Graph API:

```http
POST https://graph.microsoft.com/beta/applications/
OData-Version: 4.0
Content-Type: application/json
Authorization: Bearer <token>

{
  "@odata.type": "Microsoft.Graph.AgentIdentityBlueprint",
  "displayName": "AWS Sales Assistant Agent",
  "sponsors@odata.bind": [
    "https://graph.microsoft.com/v1.0/users/<sponsor-user-id>"
  ],
  "owners@odata.bind": [
    "https://graph.microsoft.com/v1.0/users/<owner-user-id>"
  ]
}
```

**Save the returned `appId`** — you'll need it in every subsequent step.

> **Sponsor** = the human accountable for this agent (e.g., business owner).
> **Owner** = the human who can make technical changes to the blueprint.

---

### Step 2 — Configure Credentials (Federated Identity for AWS)

Since your agent runs on **AWS, not Azure**, you cannot use Azure Managed Identities. The recommended approach is **Federated Identity Credentials (FIC)** using AWS's OIDC provider. This lets your AWS-hosted agent present an AWS token that Entra trusts — no client secrets stored on AWS.

The credential types supported for agent identities are:

| Credential Type | Best For | Recommended? |
|---|---|---|
| **Federated Identity Credentials (FIC)** | Kubernetes, AWS, GCP, other clouds | ✅ Yes — best for AWS |
| **Client certificates** | On-premises, any environment | ✅ Yes |
| **Client secrets** | Local dev/testing only | ⚠️ Not for production |
| **Managed Identities** | Azure-hosted only | ❌ Not available on AWS |

#### Option A: Federated Identity Credential with AWS OIDC (Recommended)

**On the AWS side**, configure an IAM OIDC identity provider and an IAM role that your agent's compute (ECS, Lambda, EC2) can assume. Your agent code will obtain an AWS STS token.

**On the Entra side**, add a federated credential to your blueprint that trusts the AWS OIDC issuer:

```http
POST https://graph.microsoft.com/beta/applications/<blueprint-object-id>/federatedIdentityCredentials
OData-Version: 4.0
Content-Type: application/json
Authorization: Bearer <token>

{
    "name": "aws-agent-credential",
    "issuer": "https://sts.amazonaws.com",
    "subject": "<AWS-IAM-Role-ARN-or-subject>",
    "audiences": [
        "api://AzureADTokenExchange"
    ]
}
```

> The `issuer` is AWS STS's OIDC endpoint. The `subject` must match the claim in the AWS token (typically the IAM role ARN). The `audiences` value must be `api://AzureADTokenExchange`.

For details on workload identity federation with external identity providers, see [Microsoft Entra Workload Identity Federation](https://learn.microsoft.com/en-us/entra/workload-id/workload-identity-federation).

#### Option B: Client Certificate

Generate a certificate, install the private key on your AWS compute, and register the public key:

```http
POST https://graph.microsoft.com/beta/applications/<blueprint-object-id>/addKey
Content-Type: application/json
Authorization: Bearer <token>
```

#### Option C: Client Secret (Dev/Testing Only)

```http
POST https://graph.microsoft.com/beta/applications/<blueprint-object-id>/addPassword
Content-Type: application/json
Authorization: Bearer <token>

{
  "passwordCredential": {
    "displayName": "AWS Dev Secret",
    "endDateTime": "2027-01-01T00:00:00Z"
  }
}
```

> ⚠️ **Do not use client secrets in production.** They must be stored securely and rotated manually. Use FIC or certificates instead.

---

### Step 3 — Configure Identifier URI and Scope (If Interactive)

If your agent acts **on behalf of users** (interactive pattern — e.g., a chat agent), expose a scope so the front end can pass user tokens to your AWS backend:

```http
PATCH https://graph.microsoft.com/beta/applications/<blueprint-object-id>
OData-Version: 4.0
Content-Type: application/json
Authorization: Bearer <token>

{
    "identifierUris": ["api://<blueprint-app-id>"],
    "api": {
      "oauth2PermissionScopes": [
        {
          "adminConsentDescription": "Allow the application to access the agent on behalf of the signed-in user.",
          "adminConsentDisplayName": "Access agent",
          "id": "<generate-a-guid>",
          "isEnabled": true,
          "type": "User",
          "value": "access_agent"
        }
      ]
    }
}
```

If your agent is **fully autonomous** (no user context), you can skip this step.

---

### Step 4 — Create the Blueprint Principal

This registers the blueprint's service principal in your tenant, making it operational:

```http
POST https://graph.microsoft.com/beta/serviceprincipals/graph.agentIdentityBlueprintPrincipal
OData-Version: 4.0
Content-Type: application/json
Authorization: Bearer <token>

{
  "appId": "<blueprint-app-id>"
}
```

---

### Step 5 — Get an Access Token from Your AWS Agent

Your AWS-hosted code now authenticates to Entra using the blueprint credentials.

**With FIC (AWS OIDC):**

```
POST https://login.microsoftonline.com/<tenant-id>/oauth2/v2.0/token
Content-Type: application/x-www-form-urlencoded

client_id=<blueprint-app-id>
scope=https://graph.microsoft.com/.default
client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer
client_assertion=<aws-oidc-token>
grant_type=client_credentials
```

**With client secret (dev only):**

```
POST https://login.microsoftonline.com/<tenant-id>/oauth2/v2.0/token
Content-Type: application/x-www-form-urlencoded

client_id=<blueprint-app-id>
scope=https://graph.microsoft.com/.default
client_secret=<your-secret>
grant_type=client_credentials
```

---

### Step 6 — Create Agent Identities

Using the access token from Step 5, create one or more agent identities:

```http
POST https://graph.microsoft.com/beta/serviceprincipals/Microsoft.Graph.AgentIdentity
OData-Version: 4.0
Content-Type: application/json
Authorization: Bearer <token>

{
    "displayName": "AWS Sales Assistant - North America",
    "agentIdentityBlueprintId": "<blueprint-app-id>",
    "sponsors@odata.bind": [
        "https://graph.microsoft.com/v1.0/users/<sponsor-user-id>"
    ]
}
```

Create one agent identity per agent instance. All share the same blueprint but have distinct identities for auditing and access control.

---

### Step 7 — (Optional) Register in the Agent Registry

To make your agent discoverable to users in Microsoft 365 and apply governance policies (collections, discovery controls), register it in the Agent Registry. This is separate from the identity layer and provides centralized metadata and discoverability.

---

### Summary: End-to-End Flow for AWS-Hosted Agents

```
┌─────────────────────────────────────────────────────────────┐
│                    Your Azure Entra Tenant                   │
│                                                             │
│  1. Create Blueprint ─► 2. Add FIC (AWS OIDC) credential   │
│  3. Configure scope ─► 4. Create Blueprint Principal        │
│  6. Agent identities created via Graph API                  │
└───────────────────────────┬─────────────────────────────────┘
                            │ tokens
                            ▼
┌─────────────────────────────────────────────────────────────┐
│                       AWS (your agent)                       │
│                                                             │
│  5. Agent code authenticates using AWS OIDC token + FIC     │
│     → Gets Entra access token                              │
│     → Calls Microsoft Graph / M365 APIs                    │
│     → Acts on behalf of users (OBO) or autonomously        │
└─────────────────────────────────────────────────────────────┘
```

### Key Considerations for AWS Hosting

| Concern | Guidance |
|---|---|
| **Credential type** | Use Federated Identity Credentials with AWS OIDC — no secrets to manage |
| **Tenant scope** | Agent identities can only get tokens in the Entra tenant where created |
| **Agent patterns** | Interactive (OBO with user context) or Autonomous (client_credentials) |
| **Governance** | Blueprint sponsor + owner provide accountability; Conditional Access policies apply to all identities under the blueprint |
| **Monitoring** | All agent sign-ins and identity creations appear in Entra audit logs |
