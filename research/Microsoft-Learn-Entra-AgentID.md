## What is Microsoft Entra Agent ID?

**URL:** https://learn.microsoft.com/en-us/entra/agent-id/identity-professional/microsoft-entra-agent-identities-for-ai-agents

As assistive and autonomous agents become more prevalent in organizations, new security, governance, and compliance challenges must be addressed. Microsoft Entra Agent ID extends the comprehensive security capabilities of Microsoft Entra to agents, enabling organizations to build, discover, govern, and protect agent identities.

> **Important:** Microsoft Entra Agent ID is currently in PREVIEW.

### Conditional Access for agents

Conditional Access enables organizations to define and enforce adaptive policies that evaluate agent context and risk before granting access to resources:

- Enforcing adaptive access control policies for all agent patterns across assistive, autonomous, and agent user types.
- Using real-time signals such as agent identities risk controlling agent access to resources, with Microsoft Managed Policies providing a secure baseline by blocking high-risk agents.
- Deploying conditional access policies at scale using custom security attributes, while still supporting fine-grained controls for individual agents.

### ID Governance for agents

Microsoft Entra Agent ID brings agent identities into similar identity governance processes as users:

- Govern agent identities at scale, from deployment to expiration.
- Ensure sponsors and owners are assigned and maintained for each agent ID, preventing orphaned agent IDs.
- Enforce that agent access to resources is intentional, auditable, and time-bound through access packages.

### ID Protection for agents

Microsoft Entra ID Protection detects and blocks threats by flagging anomalous activities involving agents:

- Detect agent identity risk derived from user risk and based on agents' own actions.
- Provide risk signals to conditional access to enforce risk-based policies.
- Provide risk signals to the Agent Registry to inform agent discoverability and access, with automatic remediation.

### Network controls for agents

- Log agent network activity to remote tools for audit and threat detection.
- Restrict file uploads and downloads using file-type policies.
- Detect and block prompt injection attacks that attempt to manipulate agent behavior.

### How to get started

Microsoft Entra Agent ID is part of Microsoft Agent 365. Both are available through the Frontier program in Microsoft 365. To access these features you must have a license for Microsoft 365 Copilot and have enabled Frontier for your users.

1. Sign in to the Microsoft 365 admin center as a Billing Administrator.
2. Browse to **Copilot** > **Settings** > **User access** > **Copilot Frontier** and make sure it's enabled for users.

## Security for AI

**URL:** https://learn.microsoft.com/en-us/entra/agent-id/identity-professional/security-for-ai

### Types of AI agents

- **Assistive agents** perform specific, well-defined tasks on demand.
- **Autonomous agents** operate independently, making decisions and taking actions without human intervention.
- **Agent users** are agents designed to function with human user characteristics, including persistent identities and access to organizational systems.

### Agent application security challenges

Unlike applications that execute predetermined logic, AI agents make dynamic decisions and adapt behavior based on training data, input, and environment conditions.

**Increased attack surface:**
- External accessibility creates potential pathways for adversaries.
- Permission escalation risk — agents often provisioned with broad permissions.
- Autonomous decision-making — compromised agents can take harmful actions.
- Prompt injection attacks manipulate agent behavior via malicious instructions in data.
- Agent interaction — compromised agents can propagate compromise to other agents.

**Compliance and audit issues:**
- Regulatory requirements for oversight of AI systems.
- Data privacy compliance (GDPR, CCPA).
- Audit trails documenting agent actions, data accessed, and decisions made.

### Agent sprawl

Agent proliferation creates "agent sprawl" — the uncontrolled expansion of agents without adequate visibility, management, or lifecycle controls. Patterns include shadow AI, rapid proliferation, inadequate lifecycle management, permission creep, and lost accountability.

### Agent security scenarios

| Scenario | Security challenge | Risk |
|---|---|---|
| **User-Initiated Agent** | Prevent misuse of inherited permissions | Unauthorized actions as the user |
| **Autonomous Agent** | Grant only necessary permissions | Operate without constraint |
| **Agent User** | Maintain permission scope | Access documents, send communications as trusted team member |
| **Agent-to-Agent** | Establish authenticated communication | Injection of malicious agents or interception |

### Microsoft Entra Agent ID capabilities

- **Register and manage agents**: Agent identities, agent registry
- **Govern agent identities and lifecycle**: Identity governance for agent identities
- **Protect agent access**: Global Secure Access, Conditional Access, Identity Protection

## Authorization in Microsoft Entra Agent ID

**URL:** https://learn.microsoft.com/en-us/entra/agent-id/identity-professional/authorization-agent-id

Microsoft Entra ID limits what agent identities can do. Many high privilege capabilities assume a human administrator with careful intent. An unrestrained agent with high privileges could perform unexpected administrative tasks with far reaching impact.

### Key restrictions

- Many highly privileged directory roles are **blocked** for agents (e.g., Global Administrator, Privileged Role Administrator, User Administrator).
- Only lower privileged roles can be assigned (e.g., reader roles).
- Custom roles **cannot** be assigned to agent identities.
- Agent identities **cannot** be members of role-assignable groups.
- Roles specifically for agent management: **Agent ID Administrator** and **Agent ID Developer**.

### Blocked Microsoft Graph permissions

| Blocked permission | Notes |
|---|---|
| `Application.ReadWrite.All` | Manages all applications |
| `RoleManagement.ReadWrite.All` | Full control over users, groups, roles |
| `User.ReadWrite.All` | Full control of all user accounts |
| `Directory.AccessAsUser.All` | Sweeping Microsoft Graph access |

### When to use which access type

- **Azure roles**: For agent access to Azure resources (e.g., Key Vault Reader on a specific vault).
- **Microsoft Entra roles**: Only if a suitable lower privileged role exists.
- **Delegated Microsoft Graph permissions**: When agent acts on behalf of a user (requires user consent).
- **Application permissions**: Sparingly for autonomous tenant-wide operations; only non-high-privilege.

### Allowed Entra roles for agents

A comprehensive list of ~70+ roles that CAN be assigned to agent identities is maintained in the official documentation. Notable inclusions: Global Reader, Exchange Administrator, SharePoint Administrator, Teams Administrator, Compliance Administrator, Fabric Administrator, Power Platform Administrator, etc.

## What is the Microsoft Agent Identity Platform?

The Microsoft agent identity platform is an identity and authorization framework built to address the unique authentication, authorization, and governance challenges posed by AI agents in enterprise environments. Unlike nonagentic application identities or user identities, it is purpose-built for AI agents.

### Platform architecture

- **Authentication service**: OAuth 2.0 and OIDC standard-compliant. Issues tokens for agents. Three core identity constructs: agent identity blueprint, agent identity, and agent user.
- **SDKs**: Microsoft Identity Web (.NET) and Microsoft Entra SDK for Agent ID.
- **Agent management**: Comprehensive metadata store and admin interface in Microsoft Entra admin center, including the agent registry.

### Integration and interoperability

- Extends Microsoft Entra ID capabilities for agent scenarios.
- Integrates with Copilot Studio, third-party platforms.
- Works with Conditional Access, Identity Protection, Identity Governance, Global Secure Access.

## What is an Agent Identity?

**URL:** https://learn.microsoft.com/en-us/entra/agent-id/identity-platform/what-is-agent-id

Agent identities are identity accounts within Microsoft Entra ID that provide unique identification and authentication capabilities for AI agents. They address the gap where identity models for human users and applications prove insufficient.

### What is an agent

Key components: Model (LLM), Orchestration Layer (cyclical decision process), Memory (dynamic context), Tools (web search, APIs, etc.).

### Why agent identities exist

- Distinguish AI agent operations from workforce/customer/workload identities.
- Enable right-sized access across systems.
- Prevent agents from gaining critical security roles.
- Scale identity management for agents created/destroyed dynamically.

### Agent identities vs application identities

Application identities (service principals) assume long-term stability and known ownership. Agent identities embrace dynamic nature — created in bulk, consistent policies, retired without orphaned credentials. Designed for scale and ephemerality.

### Agent identities vs human user identities

Agent identities represent software systems, not humans. They don't use human authentication mechanisms. For scenarios requiring human-like operation, agent identities can be paired with **agent users** — special Microsoft Entra user accounts with a 1:1 relationship.

### What agent identities enable

- Access web services (Graph, custom, third-party) via access tokens.
- Autonomous access using rights given directly to the agent identity.
- Delegated access on behalf of human users.
- Authenticate incoming messages from other clients, users, and agents.

## What is the Agent Registry?

**URL:** https://learn.microsoft.com/en-us/entra/agent-id/identity-platform/what-is-agent-registry

The Agent Registry provides an extensible metadata repository delivering a unified view of all deployed agents across Microsoft and non-Microsoft ecosystems.

### Critical capabilities

- **Comprehensive inventory and visibility**: All deployed agents, with or without agent identity.
- **Discovery before access**: Built-in and custom controls with agent collections and Zero Trust principles.
- **Rich metadata for governance**: Detailed metadata using open standards for collaboration.

### Architecture

- **Metadata store**: NoSQL-based, agent card manifest support, real-time updates.
- **Collections**: Baseline discovery controls, custom collections.
- **Discovery service**: Multi-dimensional search, collection-aware filtering, skill-based discovery.
- **Integration layer**: Ecosystem-wide security operations and custom workflows.

### Security

- **Identity Assurance**: Microsoft platforms fully integrated with Agent ID Platform automatically receive an agent identity and are enrolled in the registry.
- **Runtime Enforcement**: Discovery policies enforced dynamically. Only agents with agent identity can discover other agents; they can find agents without agent ID.

## Key Concepts

**URL:** https://learn.microsoft.com/en-us/entra/agent-id/identity-platform/key-concepts

### Core identity concepts

- **Agent identity**: Primary account for AI agent authentication. Has object ID and app ID (same value). No credentials on its own — uses credentials from parent blueprint.
- **Agent identity blueprint**: Template and management structure for creating/managing multiple agent identities. Serves as parent of agent identity.
- **Agent identity blueprint principal**: Created when blueprints are added to tenants. Manages the blueprint's presence within that specific tenant.
- **Agent user**: Secondary account for agents that need to interact with systems requiring user objects. Has most properties of other users (manager, UPN, photo).

### Agent operation patterns

- **Interactive agents**: Sign in a user and act on behalf of the signed-in user. Use delegated permissions. Tokens called "user tokens."
- **Autonomous agents**: Act using their own identity. Run in background, make autonomous decisions. Tokens called "agent tokens."

### Administrative relationships

- **Owners**: Technical administrators (developers/IT) handling setup, configuration, credentials.
- **Sponsors**: Business accountability for lifecycle decisions without technical admin access.
- **Managers**: Designated hiring manager or operational owner for an agent user.

## Agent Identity Blueprints

**URL:** https://learn.microsoft.com/en-us/entra/agent-id/identity-platform/agent-blueprint

An agent identity blueprint serves four purposes:

1. **Template for agent identities**: Records common characteristics shared across all agent identities (description, appRoles, verifiedPublisher, optionalClaims).

2. **Creates agent identities**: Has OAuth client ID, credentials, and `AgentIdentity.CreateAsManager` permission. Limited to 250 agent identity creations per principal.

3. **Holds credentials for agent identities**: Individual agent identities don't have their own credentials — they use the blueprint's credentials for token requests.

4. **Container for agent identities**: Policies and settings applied to blueprints take effect for all agent identities created from them (Conditional Access policies, OAuth permissions, disabling).

### Agent identity blueprint principals

When a blueprint is added to a tenant, a principal object is created:
- **Token Issuance**: Token `oid` claim references the principal.
- **Audit Logging**: Actions recorded as executed by the principal.

Blueprints can be "single-tenant" or "multitenant" (published to catalogs).

## Agent Identities

**URL:** https://learn.microsoft.com/en-us/entra/agent-id/identity-platform/agent-identities

An agent identity is a special service principal in Microsoft Entra ID. It doesn't have credentials on its own. The blueprint can acquire tokens on behalf of the agent identity.

### Anatomy

- **Identifier**: Object ID (= App ID), unique within tenant.
- **Credentials**: No passwords; uses blueprint credentials.
- **Display name**: Human-friendly name, appears in admin center, Teams, Outlook.
- **Sponsor**: Human user or group accountable for the agent.
- **Blueprint**: Parent template.
- **Agent user** (optional): Secondary user account with 1:1 relationship.

### Credential types

- Managed identities (most secure, for Azure-hosted agents).
- Federated identity credentials (for Kubernetes/other cloud).
- Certificates / cryptographic keys.
- Client secrets.

Agent identities can only be issued tokens in the tenant where created. Cannot access resources in other tenants.

## Agent Users

**URL:** https://learn.microsoft.com/en-us/entra/agent-id/identity-platform/agent-users

Agent users bridge the gap between agents and human user capabilities. They enable agents to interact with systems requiring user identities.

### When to use

- Organization needs long-term digital employees with mailboxes, chat access, HR system inclusion.
- Agent needs APIs only available to user identities.
- Agent needs to participate in collaborative workflows as a team member.

### Key characteristics

- Receive tokens with claim `idtyp=user`.
- Created explicitly with connection to parent agent identity (1:1, immutable).
- Can be added to groups (including dynamic groups, but not role-assignable groups).
- Can be assigned licenses (often needed for M365 resources).
- Can be added to administrative units.

### Security constraints

- No passwords or passkeys — only agent identity reference credential.
- Cannot be assigned privileged administrator roles.
- Permissions similar to guest users with enhanced enumeration capabilities.
- No custom role assignment.

## Agent Registry Collections

**URL:** https://learn.microsoft.com/en-us/entra/agent-id/identity-platform/agent-registry-collections

Collections define how agents are logically organized and discovered during agent-to-agent collaboration.

- Agents **with** agent identity can query the registry and discover other agents.
- Agents **without** agent identity can only be discovered (not perform discovery).

### Collection types

- **Global Collection**: Agents discoverable across the entire organization. Inherits "Discoverable by All" policy.
- **Custom collection**: Created by admins for business/policy-aligned discovery boundaries.
- **Quarantined collection**: Predefined collection to limit discovery. Agents cannot discover others.

### Discovery policies

- **System-defined**: Apply automatically to Global Collection.
- **Admin-defined**: Control discoverability based on business/departmental boundaries.

### FAQs

- Moving agents into collections is manual (can add multiple at once).
- No limit on number of custom collections.
- Preview limit: 100 agents per collection.
- Collections complement (not replace) Microsoft Entra Groups. Groups = "who can access what." Collections = "which agents can discover each other."

## Agent Metadata and Discoverability

**URL:** https://learn.microsoft.com/en-us/entra/agent-id/identity-platform/agent-metadata-discoverability

## Agent Owners, Sponsors, and Managers

**URL:** https://learn.microsoft.com/en-us/entra/agent-id/identity-platform/agent-owners-sponsors-managers

### Owners

Technical administrators handling setup, configuration, credentials. Can modify auth properties, add/update other owners and sponsors, disable/delete/re-enable agent identities. Typically developers or IT professionals. Service principals can also be owners.

### Sponsors

Business accountability without technical admin access. Make lifecycle decisions (renewal, extension, removal). Request access packages. Provide business justification. Cannot modify application settings. Can only enable/disable agents.

**A sponsor is required when creating an agent identity or agent blueprint.**

### Managers

Designated for agent users. Can request access packages. Cannot modify or delete agents.

## Tokens in Agent IDs

**URL:** https://learn.microsoft.com/en-us/entra/agent-id/identity-platform/agent-tokens

### Token claims entity identifiers

- `xms_act_fct` (Actor facet): Entity performing actions.
- `xms_sub_fct` (Subject facet): Ultimate subject for operations.
- `idtyp`: Distinguishes user vs application context.
- `xms_idrel`: Relationship between token subject and resource tenant.

### Token flow patterns

- **User delegation**: Tokens preserve user identity while identifying agent identity blueprint as actor. Maintain user identity context, include delegated permissions.
- **Application-only**: Autonomous operations. Agent identity blueprint's own identity. Application-level permissions.
- **Agent user impersonation**: Blueprint impersonates agent identity, which impersonates agent user. User-context behavior with controlled identities.

### Tenancy

All tokens bounded within tenant of agent identity. Cannot access resources outside assigned tenant.

## OAuth Protocol for Agent IDs

**URL:** https://learn.microsoft.com/en-us/entra/agent-id/identity-platform/agent-oauth-protocols

Agents use OAuth 2.0 with specialized token exchange patterns enabled by Federated Identity Credentials (FIC). All agent auth flows involve multi-stage token exchanges where the blueprint impersonates the agent identity.

### Supported grant types

**Blueprint:** `client_credentials`, `jwt-bearer` (OBO), `refresh_token`.
**Agent identity:** `client_credentials`, `jwt-bearer` (client credentials + OBO), `refresh_token`.

### Unsupported flows

- OBO flows using `/authorize` endpoint.
- Public client capabilities.
- Redirect URLs.
- Interactive flows for any agent entity type.

### Three agent OAuth flows

1. **Agent on-behalf-of flow**: Agents operating on behalf of regular users (interactive).
2. **Autonomous app flow**: App-only operations without user context.
3. **Agent user flow**: Agents operating via user principals created for agents.

### Credential recommendations

- **Managed identities** are preferred (automatic rotation, secure storage).
- **Client secrets should NOT be used in production** — use FIC with managed identities or client certificates.

## Token Claims Reference

**URL:** https://learn.microsoft.com/en-us/entra/agent-id/identity-platform/agent-token-claims

### Agent-specific claims

| Claim | Description |
|---|---|
| `xms_act_fct` | Actor facets (value `11` = AgentIdentity) |
| `xms_sub_fct` | Subject facets (`11` = AgentIdentity, `13` = AgentIDUser) |
| `xms_tnt_fct` | Tenant facets |
| `xms_par_app_azp` | Parent application of authorized party (GUID) |
| `xms_idrel` | Identity relationship (multivalued integers) |

### xms_idrel values

| Value | Description |
|---|---|
| 1 | Member user |
| 7 | Service principal |
| 9 | Device principal |
| 11 | GDAP user |
| 13 | SPLess application |
| 33 | Federated managed identity |

### Scenario-wise claims

**Agent acting on behalf of user:** `idtyp=user`, `xms_act_fct=11`, `scp` has delegated permissions.
**Agent acting autonomously:** `idtyp=app`, `xms_act_fct=11`, `xms_sub_fct=11`, `scp` empty.
**Agent via agent user:** `idtyp=user`, `xms_act_fct=11`, `xms_sub_fct=13`, `scp` has delegated permissions.

## Sign-in and Audit Logs for Agents

**URL:** https://learn.microsoft.com/en-us/entra/agent-id/identity-professional/sign-in-audit-logs-agents

### Audit logs

Agent activity logged under base identity type:
- Agent identity user → "Create user" audit activity.
- Agent identity → "Create service principal."
- Agent identity blueprint → "Delete application."

### Sign-in logs

New `agentSignIn` resource type in sign-in logs. Filter options in admin center:
- **Agent type**: Agent ID user, Agent Identity, Agent Identity Blueprint, Not Agentic.
- **Is Agent**: Yes / No.

### Microsoft Graph API

```
GET https://graph.microsoft.com/beta/auditLogs/signIns?$filter=signInEventTypes/any(t: t eq 'servicePrincipal') and agent/agentType eq 'AgentIdentity'
```

## Known Issues (Preview)

**URL:** https://learn.microsoft.com/en-us/entra/agent-id/identity-platform/preview-known-issues

### Agent identities and blueprints
- No way to filter Graph API relationship queries to return only Agent IDs (use client-side filtering).

### Agent users
- Orphaned agent users remain when blueprint/identity is deleted (delete manually).

### Roles and permissions
- Global Reader can't list agent identities via `graph.agentIdentity` endpoint (use `/servicePrincipals`).
- No viable delegated permission for creating agent identities (use application permissions).
- `Directory.AccessAsUser.All` causes other Agent ID permissions to be ignored (remove it).
- Custom roles can't include Agent ID actions (use built-in roles).
- Agent identities can't be added to administrative units.
- Agent ID Administrator can't update photos for agent users (use User Administrator).

### Admin center
- Can't create/edit blueprints through admin center (use Graph APIs/PowerShell).

### Authentication
- Agent IDs can't sign in to Microsoft Entra sign-in pages (no SSO to web apps).

### Consent and permissions
- Admin consent workflow doesn't work properly for Agent ID permissions.
- Can't grant application permissions to blueprint principals (grant to individual identities).
- Can't assign app roles where target resource is agent identity (use blueprint principal as target).

### Dynamic groups
- Can't add agent identities to groups with dynamic membership (use fixed membership).

### Performance
- Multiple rapid creation requests may fail with `400 Bad Request` (use delegated permissions, add retry with exponential backoff).

### Product integrations
- Copilot Studio: Must opt in to Agent IDs in environment settings. Only custom engine agents supported. Agent IDs only used for channel authentication, not connectors/tools.

### Libraries
- .NET: Use Microsoft.Identity.Web.AgentIdentities.
- Non-.NET: Use Microsoft Entra SDK for Agent ID.
